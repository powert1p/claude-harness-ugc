# Постановка поиска, композиция и доказательства

Читать при сложной постановке, составной нужде или спорном решении, не для каждого lookup.

## Поисковое ТЗ

До разведки достаточно намерения и известных границ. После неё собери один короткий brief в существующем anchor или статусе. Это рабочее ТЗ поиска, не новый product spec.

```text
Результат: какое решение принять / что объяснить.
Контекст: актуальные решения чата и что уже есть в проекте.
Ограничения: явные требования; отдельно допущения и неизвестное.
Разведка: найденные термины/классы + указатели на прочитанное.
Гипотезы: возможный механизм решения → подтверждающая/опровергающая проверка.
Приоритет: следующий вопрос, запрос и подходящий источник.
Достаточно: какие evidence позволят выбрать; какой пробел оставит вывод условным.
```

Не заполняй шаблон ради формы: объединяй строки, оставляй только влияющее на поиск. Направление — класс решения; гипотеза — проверяемое предположение о применимости. Не нужно искусственно делать несколько альтернатив для известного ответа. Для научного обзора/объяснения формулируй вопросы и конкурирующие объяснения, без обязательного выбора продукта.

Условный пример: пользователь пишет «найди поиск для наших документов». В чате уже выбраны offline и PostgreSQL, есть parser; объём неизвестен. Разведка выявила lexical/hybrid retrieval и OCR как возможный отдельный bottleneck. ТЗ: проверить, достаточно ли существующего индекса; помогает ли hybrid на реальных запросах; не теряется ли нужный текст ещё при извлечении. Сначала исследовать failing документ и документацию установленного стека; отдельный сервис сравнивать при доказанном пробеле. Названия и результаты разведки здесь учебные, не выполненный анализ проекта.

Исправление контекста: если раннее сообщение допускало cloud, а позднее требует offline, используй позднее. «Может, vector DB?» — гипотеза, пока владелец не сделал её требованием. Проверка должна допускать отказ от неё. Не передавай приватный контекст в публичную поисковую строку: выдели обезличенные capabilities.

## Проверка композиции

Сначала выпиши capabilities без привязки к поставщику. Для каждой: существующее в проекте, кандидат, ограничения, evidence и незакрытая часть. Концепт даёт механизм и словарь поиска; reference implementation дополнительно даёт проверяемый код, но её лицензию и production-пригодность ещё нужно проверить.

Проверь только существенные для этой задачи стыки:
- вход/выход: формат, schema, units, encoding, IDs, ограничения размера;
- runtime: версии, OS, sync/async, deployment, CPU/GPU, локально/cloud;
- поведение: ошибки, retry, idempotency, порядок, потеря данных;
- эксплуатация: лицензия, платные лимиты, поддержка и стоимость glue.

Запиши владельца каждого перехода. «A отдаёт текст, B принимает текст» недостаточно, если B требует document ID или chunk metadata. Выбери probe, который скорее всего опровергнет композицию, и проверь его перед объявлением готовности. Называй отдельно docs compatibility и фактический end-to-end результат.

Пример: LocalParse → OCR для сканов → index/search + существующая очередь. Можно Adopt отдельные части и Build ID/retry glue, сохранив Compose для целого. Пять частей сами по себе не означают пять проектов. Если есть единый пакет, сравни не только количество кода, но и его ограничения, настройку, миграцию и дальнейшее владение.

## Поиск и отрицательные результаты

В глубоком research храни компактный журнал:

| Вопрос | Запрос/канал | Что прочитано | Результат для решения | Следующий пробел |
|---|---|---|---|---|
| Нужен offline OCR | exact → соседний класс → официальные docs | URL, версия, дата | cloud-кандидат исключён; локальная часть найдена | проверить PNG и язык |

Если выдача однообразна, меняй capability, термин, класс или первоисточник. Citation chasing — переход к процитированному стандарту, реализации или исследованию, когда он закрывает конкретный пробел. Не размножай поиски по языкам и сервисам ради объёма.

Нет точного продукта → ищи реализации частей и подходы. Нет результатов из-за timeout → восстанавливай retrieval. Эти ситуации требуют разных действий. Невозможно доказать отсутствие всех решений; обоснуй выбор в пределах проверенного покрытия.

Для решающего утверждения запиши источник и scope: «docs v3: local ≤20 MB» не доказывает лимит v2. Два перепечатавших источник сайта — один origin. При разногласии сохрани обе версии и проведи решающий probe; если он невозможен, оставь unknown.

## Откуда взят метод

Проверено 2026-09-06; это основания подхода, а не обязательные внешние чтения для каждой задачи.

- [CMU SEI, COTS-Based Systems](https://www.sei.cmu.edu/library/cots-based-systems/), 2017: требования, рынок готовых продуктов и архитектура рассматриваются совместно. Применение здесь: не замораживать разбиение задачи до изучения существующих решений.
- [Anthropic, Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), 2025: поиск уточняется по находкам; bounded задания и выбор инструментов важнее жёсткой траектории. Их модельные benchmark-цифры не переносятся на Codex/Astra.
- [Marcia J. Bates, Berrypicking](https://pages.gseis.ucla.edu/faculty/bates/berrypicking.html), 1989: находки меняют запрос и понимание нужды; простой однозначный запрос может завершиться одним поиском. Историческая модель информационного поиска, не эксперимент с современными AI.
- [Cochrane, Searching and selecting studies](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-04): словарь, покрытие и документирование поиска. Заимствованы принципы поиска; полный clinical systematic review для coding research не требуется.

Локальная адаптация: намерение → разведка → компактное поисковое ТЗ → готовое/соседние подходы → композиция → минимальный собственный остаток. Формат brief и его размер — наше engineering решение, а не доказанный универсальный оптимум или дословный алгоритм источника.
